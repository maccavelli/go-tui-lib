# Move the toolchain floor to Go 1.27.2, the release that fixes GO-2026-6604

## Context and Problem Statement

On 2026-10-08 the Go vulnerability database added GO-2026-6604
(CVE-2026-56857, published 22:31Z): "Root.Mkdir(All) can follow junctions
out of the root on Windows in os". It affects every Go 1.27 release before
1.27.2, and every earlier one before 1.26.9. Go 1.27.2 and 1.26.9 are
released (`https://go.dev/dl/?mode=json`).

govulncheck reports it as called by this repository's code:

```text
Vulnerability #1: GO-2026-6604
  Found in: os@go1.27.1
  Fixed in: os@go1.27.2
  Platforms: windows
  #1: tuitest/tuitest.go:187:28: tuitest.compare calls os.Root.WriteFile,
      which eventually calls os.doInRoot[int]
```

`tuitest` writes a golden file through an `os.Root`, so that a golden name
cannot escape its directory. It does so only when goldens are being
updated.

So `make vuln` and `make release-check` fail on `main`. The machine-wide
commit gate runs the same precheck, so 0014-PLAN-component-native-forms
Step 7 cannot be committed (its D8). CI's `govulncheck` step will fail on
its next run.

The toolchain is set in four places, all at 1.27.1:

| Where | What | Read |
| :--- | :--- | :--- |
| `go.mod` | `go 1.27.1`, with no `toolchain` line | 0001-MADR §3 |
| `go.work` | `go 1.27.1` | CI reads it: `setup-go`'s `go-version-file: go.work` |
| this host | `GOTOOLCHAIN=go1.27.1` in the Go env file | `go env GOENV` |
| the Windows test host | `GOTOOLCHAIN=go1.27.1`, Go under `sdk\go1.27.1` | a read-only probe |

The rules that apply:

* **`AGENTS.md`, API convention 11:** the `go` line moves only by a record,
  "to the newest patch of a release Go still supports".
* **0001-MADR §3:** `go.mod` says `go 1.27.1`, "with no `toolchain` line,
  as go-core-lib".
* **The fleet rule** 0001 cites, magic-cli-remote
  `0169-MADR-standardize-toolchains-on-current-supported-advisory-free-releases.md`:
  toolchains are current, supported and free of advisories. 1.27.1 is no
  longer advisory-free.

Which toolchain should this repository require and build with, and how
does the change reach consumers?

## Decision Drivers

* The gates are honest again: `make vuln` passes without excluding an
  advisory.
* The fleet rule and API convention 11 are followed as written.
* One source of truth for the version, which CI already reads.
* Consumers (pi-go, gobble) are not forced onto a toolchain for nothing.
  But the library should not keep accepting a toolchain with a known
  advisory in code it ships.

## Considered Options

* **A. Raise the `go` line to 1.27.2** in `go.mod` and `go.work`, with no
  `toolchain` line; both hosts move `GOTOOLCHAIN` to `go1.27.2`.
* **B. Keep `go 1.27.1`, and add `toolchain go1.27.2`** to `go.mod` and
  `go.work`.
* **C. Change the hosts and CI only:** `GOTOOLCHAIN=go1.27.2` on both
  hosts, and a literal `go-version: 1.27.2` in CI. The files stay at
  1.27.1.
* **D. Exclude GO-2026-6604 from govulncheck** until a later release.

## Decision Outcome

Chosen option: **"A. Raise the `go` line to 1.27.2"**, because it is what
API convention 11 and the fleet rule prescribe. It keeps one version, in
the files CI already reads. It also means no build of this module can
use a toolchain with the advisory.

* **`go.mod` and `go.work`:** `go 1.27.2`. There is still no `toolchain`
  line.
* **This host and the Windows test host:** `go env -w
  GOTOOLCHAIN=go1.27.2`. The 1.27.1 `go` command then fetches the 1.27.2
  toolchain from the module proxy, checked against the checksum database,
  and runs it. Nothing is unpacked by hand. These are changes to each
  host's Go settings, which the PLAN names and the owner approves.
* **CI:** no change to the workflow. `setup-go` reads `go 1.27.2` from
  `go.work`.
* **The documents** that name 1.27.1 as the requirement say 1.27.2:
  * `AGENTS.md`, its intro and API convention 11;
  * `README.md`;
  * `docs/architecture.md`.

  Earlier records keep their 1.27.1: they describe what was true then.
* **The release.** `v0.8.0` carries the new floor, with W2 and W3.
  * `main` already holds unreleased W2 work, so a `v0.7.2` from `main`
    would not be a patch.
  * A `v0.7.2` from `v0.7.1` would need a release branch, which this
    repository has never used.
  * The fix itself lives in the consumer's toolchain: a consumer on
    1.27.2 is not affected, whatever this module's `go` line says.
  * The release notes for `v0.8.0` name the new floor and the advisory.

### Consequences

* Good, because `make vuln` passes with nothing excluded, so 0014's W2 can
  resume and `v0.8.0` can be tagged.
* Good, because the floor follows the rule the repository already states,
  with the reason recorded.
* Good, because CI follows with no workflow change.
* Bad, because a consumer must use Go 1.27.2 or later to build `v0.8.0`.
  With `GOTOOLCHAIN=auto`, the default, `go get` raises the consumer's
  own `go` line and fetches the toolchain. A consumer pinned to 1.27.1
  must move.
* Neutral, because go-selfupdate-lib, which this module requires, still
  says `go 1.27.1`. A requirement's lower floor is allowed. That
  repository's own gates will meet the same advisory, which is its
  decision.

### Confirmation

* `go version` on both hosts reports go1.27.2. `go env GOTOOLCHAIN` says
  `go1.27.2`.
* `make vuln` reports no called vulnerability, and `make release-check` is
  clean, on both hosts.
* CI on the commit passes, with `setup-go` reporting Go 1.27.2.
* `go mod tidy -diff` is clean, and `scripts/go-modules.sh --check`
  passes.

## Pros and Cons of the Options

### A. Raise the `go` line to 1.27.2

* Good, because it follows API convention 11, the fleet rule and 0001 §3
  (no `toolchain` line).
* Good, because one version, in the files CI reads.
* Bad, because it raises every consumer's minimum.

### B. Keep `go 1.27.1`, add `toolchain go1.27.2`

* Good, because consumers' minimum stays 1.27.1. A `toolchain` line in a
  dependency is ignored by its consumers.
* Bad, because it breaks 0001 §3's "no `toolchain` line" rule, which
  would need amending.
* Bad, because the module still declares it builds with an advisory-bound
  toolchain, against the fleet rule.

### C. Hosts and CI only

* Good, because no file a consumer sees changes.
* Bad, because CI stops reading its version from `go.work`, so two
  versions can drift apart.
* Bad, because the `go` line still names a release with an advisory.

### D. Exclude the advisory

* Bad, because it is a workaround that turns a gate off. The global rules
  exclude it.
