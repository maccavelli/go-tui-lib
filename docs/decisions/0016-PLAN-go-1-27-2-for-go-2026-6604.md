### Step 2: both hosts

#### Deviations

* **D1 (2026-10-08): the Windows host's SSH sessions kept go1.27.1.**
  * **Found:** `go env -w GOTOOLCHAIN=go1.27.2` on the Windows test host
    wrote its Go env file. But Go warned "go env -w GOTOOLCHAIN=... does
    not override conflicting OS environment variable", and a new SSH
    session still ran go1.27.1, with `$GOTOOLCHAIN` set to `go1.27.1`.
  * **Where it is not:**
    * the user environment variable already reads `go1.27.2`, through
      `HKCU\Environment` and `[Environment]::GetEnvironmentVariable`
      for the user;
    * there is no machine-level variable;
    * it is in none of the bash profiles, or `~/.ssh/environment`;
    * `sshd_config` leaves `PermitUserEnvironment` unset.

    So the sessions most likely carry an environment the sshd service
    captured before the user variable changed.
  * **The owner's choice,** of three: the owner restarts sshd on the host,
    or signs out and in. The agent then checks, in a fresh SSH session,
    that `go version` is go1.27.2.
  * **The others:** the agent restarts sshd over SSH, which needs an
    elevated session and drops the connection; or more read-only probing
    first.
  * **Not offered,** being a workaround: forcing `GOTOOLCHAIN` inside each
    remote run script.
* **D2 (2026-10-08): a stray sshd served the connections, and stopping
  it lost the host.**
  * **Found, after the owner restarted sshd (D1's choice):** a fresh
    session still ran go1.27.1. The owner's restart had worked: the
    service's sshd was a new process, started 19:53:05 under
    `services.exe`. But the session's process chain led elsewhere:
    `powershell` → `bash` (×4) → sshd 33092 (started 19:20:19) → sshd
    14324 (started 19:20:18), whose parent had exited. That second sshd
    pair, not the service, was answering connections. It carried the
    environment of whatever started it at 19:20, with
    `GOTOOLCHAIN=go1.27.1`.
  * **More of the same probe:**
    * the session's own environment said `go1.27.1`;
    * the user variable said `go1.27.2`;
    * there was no machine variable, and none in any profile;
    * this host's SSH client sends no `GOTOOLCHAIN`: `SendEnv` is `LANG
      LC_*`, and the variable is unset here.
  * **The owner's choice,** of three: the agent stops the stray sshd over
    SSH, and the owner fixes the host if the service then does not
    answer.
  * **The others:** the owner stops it at the machine; or no change while
    the owner finds what started it.
  * **What the agent did:**
    1. A script stopped sshd 14324, the pair's parent, and restarted the
       service. It reported "stopped sshd 14324", "restarted the sshd
       service", "service: Running".
    2. A fresh session still came through 33092: the child was the
       listener, and 14324 had only started it. That was a misreading of
       the chain, which showed 33092 as the sessions' parent.
    3. The same script for 33092 went out over that session. It returned
       no output, so whether 33092 stopped and the service restarted is
       not known. It was abandoned after 180 s.
  * **The outcome:** the host's SSH port accepts a TCP connection, but a
    login gets no answer. A bounded attempt was abandoned after 30 s. The
    agent cannot reach the host, and the owner was asked to repair sshd
    at the machine: stop every sshd, then start the service alone.
  * **Not yet verified:** that the host runs go1.27.2 over SSH. Step 2
    stays open until a fresh session does, from the service's sshd. Steps
    3 and 4 wait for it.
  * **Resolved (2026-10-08).** The owner restarted the sshd service at the
    machine. A fresh session then ran `go version go1.27.2
    windows/amd64`, with `$GOTOOLCHAIN` and `go env GOTOOLCHAIN` both
    `go1.27.2`. Its chain is now `services.exe` → sshd 24748 (the service,
    started 20:10:04) → sshd 8544 → sshd 36104 (the connection). No other
    sshd runs.
  * **Not done, being a workaround:** forcing `GOTOOLCHAIN` in the remote
    run scripts.
